# 官方预设规则对局平台设计方案

**日期**: 2026-04-24
**范围**: 将当前单一狼人杀规则升级为可选择官方预设规则的对局平台。实现时会修改 `apps/api` 和 `apps/web`，但第一阶段不做用户自定义规则编辑器。

## 1. 背景

当前系统已经支持发起、实时观战和复盘一局狼人杀对局，但规则被写死在后端引擎、配置和中文 prompt 中。具体包括固定 8 人身份分配、固定夜晚行动、固定胜利条件，以及前端创建对局时只提供随机种子和最大轮数。

下一步目标是把产品从“一个固定规则的模拟器”升级为“可选择官方规则包的对局平台”。用户选择平台提供的标准玩法，系统保证规则描述、身份分配、引擎流程、直播事件和复盘展示一致。

## 2. 目标

- 创建对局时可以选择官方预设规则。
- 第一版提供 3 个官方规则：
  - 经典 8 人局。
  - 新手 6 人快局。
  - 无神职心理局。
- 保留少量房间参数：随机种子、最大轮数、好人模型、狼人模型。
- 每局保存 `rule_set_id`、规则版本和规则快照，避免未来规则更新影响历史复盘解释。
- 直播页和复盘页展示本局规则名称、版本、人数和角色构成。
- 规则配置驱动身份分配和 prompt 规则说明，减少硬编码。

## 3. 非目标

- 不做玩家自由编辑规则。
- 不做规则市场、用户上传规则或分享规则。
- 不在第一阶段加入女巫、猎人、守卫、白痴等会改变死亡结算和额外行动链的新角色。
- 不做多人房间、匹配、权限或赛季榜单。
- 不改变现有实时事件通道和复盘日志的基本形态。

## 4. 推荐方案

采用 **官方规则注册表 + 规则快照入局 + 少量参数可调**。

后端提供一个只读规则注册表，集中定义官方规则。创建对局请求传入 `rule_set_id`，后端从注册表读取规则，生成玩家、身份、行动流程和 prompt 文案。对局开始时把规则快照写入运行记录和最终日志，前端展示规则信息时优先使用快照。

这种方案比直接在前端写死选项更稳，因为引擎、prompt 和 UI 可以共享同一个规则来源；也比第一版就做规则编辑器更轻，能先把平台体验和日志兼容性打牢。

## 5. 官方规则 MVP

### 5.1 经典 8 人局

- `id`: `classic_8`
- `version`: `2026.04`
- 玩家数: 8
- 身份: 2 狼人、1 预言家、1 医生、4 村民
- 夜晚行动: 狼人袭击、医生保护、预言家查验
- 白天行动: 发言竞价、公开发言、投票放逐、回合总结
- 胜利条件: 好人放逐全部狼人获胜；狼人数量大于或等于其他存活玩家数量时狼人获胜
- 用途: 当前默认玩法，保证旧体验平滑迁移

### 5.2 新手 6 人快局

- `id`: `starter_6`
- `version`: `2026.04`
- 玩家数: 6
- 身份: 1 狼人、1 预言家、1 医生、3 村民
- 夜晚行动: 狼人袭击、医生保护、预言家查验
- 白天行动: 发言竞价、公开发言、投票放逐、回合总结
- 胜利条件: 与经典局一致
- 用途: 更快完成一局，适合本地调试、模型 smoke test 和快速观察

### 5.3 无神职心理局

- `id`: `social_8`
- `version`: `2026.04`
- 玩家数: 8
- 身份: 2 狼人、6 村民
- 夜晚行动: 狼人袭击
- 白天行动: 发言竞价、公开发言、投票放逐、回合总结
- 胜利条件: 与经典局一致
- 用途: 去掉查验和保护，重点观察模型的发言、欺骗、怀疑链和投票推理

## 6. 规则数据模型

后端新增规则定义模块，建议放在：

```text
apps/api/app/werewolf/rules.py
```

核心结构：

```python
@dataclass(frozen=True)
class RoleSpec:
    role: str
    count: int
    team: str
    model_group: str

@dataclass(frozen=True)
class RuleSet:
    id: str
    version: str
    name: str
    description: str
    player_count: int
    roles: tuple[RoleSpec, ...]
    night_actions: tuple[str, ...]
    day_actions: tuple[str, ...]
    win_condition: str
    reveal_policy: str
```

`model_group` 用于决定角色默认使用哪类模型配置：狼人使用 `werewolf_model`，好人阵营使用 `villager_model`。第一阶段不需要为每个角色单独选模型。

运行和日志中保存规则快照：

```json
{
  "rule_set": {
    "id": "classic_8",
    "version": "2026.04",
    "name": "经典 8 人局",
    "player_count": 8,
    "roles": [
      {"role": "狼人", "count": 2, "team": "werewolves"},
      {"role": "预言家", "count": 1, "team": "villagers"},
      {"role": "医生", "count": 1, "team": "villagers"},
      {"role": "村民", "count": 4, "team": "villagers"}
    ]
  }
}
```

## 7. 后端行为

### 7.1 API

新增或扩展 API：

```text
GET  /api/v1/games/rule-sets
POST /api/v1/games/runs
```

`GET /api/v1/games/rule-sets` 返回官方规则列表，供创建对局页渲染选择器。

`POST /api/v1/games/runs` 请求增加 `rule_set_id`：

```json
{
  "rule_set_id": "classic_8",
  "villager_model": "deepseek-chat",
  "werewolf_model": "deepseek-chat",
  "seed": 21,
  "max_rounds": 8
}
```

如果没有传 `rule_set_id`，后端默认使用 `classic_8`，保持现有调用兼容。

### 7.2 初始化玩家

`initialize_game_state()` 从固定 8 人初始化改为接收 `RuleSet`。它根据规则中的角色顺序和数量生成玩家，并为狼人写入队友视角。

`choose_player_names()` 的 `player_count` 使用规则人数，而不是固定默认值。

### 7.3 夜晚行动

第一阶段只支持已有行动类型：

- `remove`: 狼人袭击。
- `protect`: 医生保护。
- `investigate`: 预言家查验。

引擎根据规则的 `night_actions` 判断是否运行对应行动。无神职心理局不会运行医生保护和预言家查验。

### 7.4 Prompt

`prompts_zh.py` 的规则说明不再写死玩家数量和身份组合。后端根据 `RuleSet` 生成中文规则说明，并放入 `world_state`，例如：

```text
共 6 名玩家：1 名狼人、1 名预言家、1 名医生、3 名村民。
夜晚：狼人选择一名玩家出局；医生保护一名玩家；预言家查验一名玩家身份。
```

行动 instruction 保持按行动类型生成。对于规则中不存在的行动，引擎不会请求模型执行。

### 7.5 胜利条件

第一阶段所有规则使用同一胜利条件：

```text
好人阵营放逐全部狼人即获胜；狼人数量大于或等于其他存活玩家数量时狼人获胜。
```

代码上仍通过 `RuleSet.win_condition` 保存标识，方便后续加入屠边、第三方阵营等规则。

## 8. 前端行为

创建对局页从普通表单升级为规则选择台：

- 规则卡片列表：名称、人数、复杂度、预计时长、简介。
- 角色构成预览：例如 `2 狼人 / 1 预言家 / 1 医生 / 4 村民`。
- 参数区：随机种子、最大轮数、好人模型、狼人模型。
- 默认选中 `classic_8`。

直播页和复盘页展示规则摘要：

- 规则名和版本。
- 玩家数。
- 角色构成。
- 当前可见参数：最大轮数、模型配置、随机种子。

前端类型增加 `RuleSetSummary`，`GameRun` 和复盘详情增加可选 `rule_set` 字段。为了兼容旧日志，缺失规则信息时显示“经典 8 人局”或“旧版规则”。

## 9. 兼容性

- 旧的 `POST /games/runs` 请求不传 `rule_set_id` 时仍可创建经典 8 人局。
- 旧 replay 如果没有 `rule_set` 字段，前端按经典 8 人局展示，不阻塞复盘。
- 日志新增字段只做向后兼容扩展，不删除现有字段。
- 现有事件类型不变，`game_started` 和 `run_created` 的 payload 增加 `rule_set`。

## 10. 错误处理

- 未知 `rule_set_id`: 返回 422 或 400，并提示规则不存在。
- 规则配置不合法: 服务启动或测试阶段失败，避免运行中才报错。
- 规则人数超过可用玩家名数量: 规则注册表校验失败。
- 无神职规则中不存在的行动不能进入 prompt 生成链路。
- 前端规则列表加载失败时，创建按钮禁用并显示简短错误。

## 11. 测试策略

后端：

- 规则注册表返回 3 个 MVP 官方规则。
- 每个规则的角色总数等于玩家数。
- 创建 run 未传 `rule_set_id` 时默认 `classic_8`。
- `starter_6` 初始化 6 名玩家和正确身份数量。
- `social_8` 不执行 `protect` 和 `investigate`。
- prompt 中的玩家数量、身份构成和夜晚行动跟规则一致。
- `game_started` 事件和落盘日志包含规则快照。

前端：

- 创建页渲染官方规则卡片。
- 默认选中经典 8 人局。
- 切换规则时角色构成预览更新。
- 提交创建对局时发送 `rule_set_id`。
- 直播页展示规则摘要。
- 旧 replay 缺少规则信息时仍可正常展示。

## 12. 后续扩展

第二阶段可以加入更多官方规则，但每个新规则都应该先确认是否需要新的引擎能力：

- 女巫局：需要解药、毒药和一次性道具状态。
- 猎人局：需要出局后开枪流程。
- 守卫局：需要连续守护限制。
- 警长局：需要额外竞选阶段和票权规则。
- 赛季规则：可以把 `RuleSet.version` 用于榜单、模型胜率和跨版本比较。

这些扩展应通过新增行动、阶段或结算策略实现，而不是把复杂逻辑塞进 prompt 文案。

## 13. 推荐实施顺序

1. 新增后端 `RuleSet` 注册表和校验测试。
2. 让 `initialize_game_state()` 按规则分配玩家身份。
3. 让引擎按规则决定夜晚行动。
4. 让 prompt 从规则快照生成中文规则说明。
5. 扩展 run API、实时事件和日志，保存规则快照。
6. 前端新增规则列表 API、规则选择 UI 和类型。
7. 直播页与复盘页展示规则摘要。
8. 补齐三类规则的后端和前端测试。
