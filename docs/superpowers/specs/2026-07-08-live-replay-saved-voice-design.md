# Live Replay Saved Voice Design

## Context

The live voice path already persists generated TTS as derived data:

- `voice_utterances` stores one logical spoken unit with speaker, text, event alignment, audio format, and completion status.
- `voice_audio_chunks` stores ordered binary audio chunks for each utterance.
- The live WebSocket can replay a recent stored utterance for a late live connection.

The mobile historical live replay page reuses the live theater UI, but it currently receives only `GamePlayback.events`. It has no saved voice data and does not connect the voice control. Users who enabled voice during a live game should be able to hear the same saved generated voice during historical replay without triggering new TTS generation.

## Goal

Expose completed saved voice utterances through the playback payload and let the mobile live replay page play them locally in sync with the replay director.

## User Decision

Use the playback API payload approach:

- Extend `GET /api/v1/games/{session_id}/playback` with a `voices` field.
- The field contains replay-ready voice messages built from saved `voice_utterances` and `voice_audio_chunks`.
- The mobile replay page consumes that local voice queue instead of opening the live voice WebSocket.

## Scope

In scope:

- Return saved, completed, public voice utterances for a session in the playback payload.
- Include all audio chunks needed for local replay playback.
- Keep replay voice aligned to `source_event_id`.
- Add a mobile replay voice hook that reuses the existing audio scheduler behavior and theater voice button shape.
- Keep live voice streaming behavior unchanged.
- Keep subtitles and text replay working when no saved voice exists.

Out of scope:

- Regenerating missing voice during replay.
- Backfilling voice for old records that never generated or persisted audio.
- Adding per-player voice assignment.
- Adding download/export of audio files.
- Changing desktop replay behavior.
- Replacing database chunk storage with object storage.

## Backend Design

### Playback Voice Shape

Add `voices` to the `GamePlayback` payload:

```json
{
  "session_id": "game_1234abcd",
  "status": "complete",
  "rule_set": {},
  "resumable": false,
  "events": [],
  "voices": [
    {
      "utterance_id": "voice_abc",
      "source_event_id": 12,
      "last_source_event_id": 12,
      "speaker_kind": "player",
      "speaker_name": "阿青",
      "mime_type": "audio/L16",
      "audio_format": "pcm",
      "sample_rate": 24000,
      "duration_ms": 900,
      "chunks": [
        {
          "chunk_index": 0,
          "data": "YWJj"
        }
      ]
    }
  ]
}
```

This shape is intentionally close to the live WebSocket protocol while avoiding an artificial WebSocket envelope in the REST response.

### Voice Store Query

Add a `DatabaseVoiceStore.list_playback_voices()` method that:

- filters by `session_id`;
- includes only `status == "complete"`;
- includes only `speaker_kind in ("player", "judge")`;
- includes only rows with `sample_rate > 0`;
- requires at least one audio chunk;
- orders by `source_event_id`, then `utterance_id`, then `chunk_index`;
- base64 encodes each chunk for JSON transport.

The method should return plain dictionaries so the route can merge them directly into the playback payload.

### Live Event Alignment

Saved voice `source_event_id` values come from the real live event stream, not from the synthetic event stream generated by `build_replay_playback()`. The playback route must preserve this alignment.

Add a `DatabaseLiveStore.playback_events_for_session(session_id)` method that:

- selects the latest persisted live run for the session that has events;
- returns those events ordered by `event_id`;
- serializes them with the existing `LiveEvent.to_dict()` shape;
- rewrites `run_id` to `playback_{session_id}` for the playback payload while preserving each event `id`.

When persisted live events exist, `/playback` should use them as `events` and may attach `voices`. When persisted live events do not exist, `/playback` should keep using `build_replay_playback()` and return `voices: []`, because saved voice event IDs cannot be trusted against the synthetic timeline.

### Route Integration

`get_game_playback()` still loads the replay session so the existing status, rule set, resumable, and 404 behavior remain unchanged. It then:

1. builds the existing synthetic playback payload as the fallback;
2. checks `DatabaseLiveStore(db).playback_events_for_session(session_id)`;
3. replaces `payload["events"]` with persisted live events only when at least one persisted event exists;
4. adds saved voices only when persisted live events are used.

If the voice query fails because the voice tables are unavailable, playback should still return events with `voices: []`. A corrupt or missing replay payload should continue to return the existing 404.

## Frontend Design

### Types

Extend `GamePlayback` with:

```ts
export type PlaybackVoiceChunk = {
  chunk_index: number;
  data: string;
};

export type PlaybackVoiceUtterance = {
  utterance_id: string;
  source_event_id: number;
  last_source_event_id: number;
  speaker_kind: "player" | "judge";
  speaker_name: string;
  mime_type: string;
  audio_format: string;
  sample_rate: number;
  duration_ms: number | null;
  chunks: PlaybackVoiceChunk[];
};
```

`voices` should default to an empty array when the backend omits it, so older servers do not break the page.

### Replay Voice Hook

Add a hook in the shared game client, tentatively `usePlaybackVoice()`:

```ts
usePlaybackVoice(voices, {
  currentEventId,
  enabled,
  isPaused,
})
```

Responsibilities:

- expose the same UI contract as `useLiveVoiceStream`: `connectionState`, `currentSpeakerName`, `errors`, and `unlockAudio`;
- unlock the same PCM audio scheduler on user tap;
- enqueue only utterances whose `source_event_id` has been reached by the director;
- play one utterance at a time in event order;
- pause and resume with the replay director;
- mark an utterance consumed after the audio clock drains;
- report a user-readable playback error and continue with text replay when audio cannot play.

Connection state mapping:

- `idle` when disabled;
- `open` when enabled and at least one saved voice is available;
- `unavailable` when enabled but no saved voice is available;
- `error` only for local audio playback failures.

The hook should reuse existing queue and PCM scheduling utilities where practical. If private helper extraction is needed, it should stay within `packages/game-client/src/live/liveVoiceStream.ts` or a small adjacent module to avoid duplicating audio scheduling logic.

### Mobile Replay Page

`LiveReplayPage` adds local voice state:

- `voiceEnabled` local state.
- `const voice = usePlaybackVoice(playback?.voices ?? [], { currentEventId, enabled: voiceEnabled, isPaused: director.isPaused })`.
- The existing theater voice button receives `onToggleVoice`, `voiceEnabled`, and `voiceState`.

The toggle behavior should match live:

- clicking from off calls `voice.unlockAudio()`;
- if unlock succeeds, voice is enabled;
- clicking while on disables voice;
- clicking while in error retries by toggling off and on.

When no saved voice exists, the button can show the existing unavailable state and the notice should explain that this replay has no saved voice.

## Data Flow

```text
Live TTS generation
  -> voice_utterances / voice_audio_chunks
  -> GET /games/{session_id}/playback
  -> GamePlayback.voices
  -> usePlaybackVoice
  -> MobileLiveTheater voice controls
  -> local PCM scheduler
```

No replay request should call the vendor TTS service.

## Error Handling

Backend:

- Missing replay session remains 404.
- Voice query failure logs a warning and returns `voices: []`.
- Invalid stored voice rows are skipped.
- Empty chunk lists are skipped.

Frontend:

- Missing or empty `voices` means voice is unavailable, not a page error.
- Malformed voice entries should be ignored by defensive filtering.
- Audio unlock or scheduling failure should add an error notice and consume the failed utterance so the replay can continue.
- Subtitles remain the reliable fallback.

## Testing

Backend tests:

- `DatabaseLiveStore.playback_events_for_session()` returns persisted events for the latest eventful run and preserves event IDs.
- `DatabaseVoiceStore.list_playback_voices()` returns only completed chunked public utterances ordered by event.
- Playback API includes `voices` with base64 chunks when persisted live events exist.
- Playback API still returns events with `voices: []` when no voice exists.
- Playback API keeps `voices: []` when it must fall back to synthetic playback events.
- Playback API continues to return 404 for missing sessions.

Game client tests:

- Playback voice reports unavailable when no saved voices exist.
- Playback voice unlocks audio before enabling playback.
- Playback voice schedules PCM chunks when the current event reaches `source_event_id`.
- Playback voice pauses and resumes with the director.
- Playback voice skips utterances before their source event.

Mobile replay tests:

- `LiveReplayPage` renders the voice button when playback includes saved voice.
- Clicking voice calls the playback voice unlock path.
- No saved voice shows a disabled unavailable voice state.
- Existing playback, phase selection, subtitles, and resume behavior continue to pass.

## Risks

- The current live voice hook owns some useful audio scheduling helpers as private implementation details. Extracting too much could destabilize live voice, so shared code should be small and test-guided.
- Stored PCM chunks can make playback payloads large. This is acceptable for the current single-user local scope, but object storage or chunked REST streaming may be needed later.
- Historical replay events are synthesized from saved game records when durable live events are unavailable. In that fallback mode the route should suppress saved voices instead of risking misaligned playback.
