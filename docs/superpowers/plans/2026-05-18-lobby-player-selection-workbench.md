# 创建对局选人流程与玩家库联动开发文档

## 目标

下一版优先完善“创建对局前的选人体验”，把当前已有的虚拟玩家库真正接入组局流程。用户在 `/games` 对局大厅中选择规则后，应能像组一桌狼人杀一样完成座位安排、虚拟玩家选择、阵容预览和发起对局，而不是只在表单里零散配置参数。

本轮不扩展“人设大脑”和长期成长系统。重点放在更基础、收益更直接的体验：让已创建的虚拟玩家可以被顺畅地选择、预览、替换、清空和用于开局。

## 当前上下文

现有功能已经具备以下基础：

- `/players` 是独立虚拟玩家工作台，可以创建、编辑、复制、删除虚拟玩家。
- 虚拟玩家支持模型、性格、人物形象、头像上传、标签、策略倾向和 prompt 预览。
- `/games` 对局大厅已经可以读取玩家库，并在 `PlayerConfigPanel` 中按座位选择虚拟玩家。
- 创建对局时，前端会把座位配置规范化为 `player_configs` 传给后端。
- 后端会在开局时冻结玩家快照，保证已开局对局不受之后编辑档案影响。

当前体验的主要不足：

- 座位区和玩家选择区只是“可用”，还没有形成明确的开局前组局台。
- 选中座位、待选择玩家、已确认玩家之间的状态层级不够清楚。
- 玩家卡片信息偏少，不能快速判断这个玩家适合放在哪个座位。
- 缺少阵容整体预览，例如已选人数、模型分布、性格分布、空席提醒。
- 缺少快速操作，例如随机填充、清空座位、收藏优先、按标签筛选。
- 玩家库为空或读取失败时，创建对局流程的引导还可以更清晰。

## 推荐方案

将 `/games` 中的创建区域升级为“开局组局台”，但保留现有架构：

- `CreateGameRunForm` 继续负责创建对局表单、规则选择、提交和导航。
- `PlayerConfigPanel` 升级为主要选人工作区。
- `/players` 继续负责虚拟玩家创建和编辑。
- 前端只消费现有 `GET /api/v1/player-profiles` 和 `POST /api/v1/games/runs`，第一阶段不新增后端 API。
- 后端校验和运行时快照逻辑保持现状，只在必要时补充测试。

本轮优先做前端体验和测试，不改变玩家档案数据模型。

## 非目标

本轮不做以下内容：

- 不做虚拟玩家长期成长或赛后学习。
- 不做阵容模板持久化。
- 不做多人在线房间。
- 不做拖拽排序作为第一优先级。
- 不做新增后端筛选 API；玩家筛选先在前端完成。
- 不在创建对局页内编辑完整玩家档案；编辑仍跳转 `/players`。

## 用户流程

### 基础流程

1. 用户进入 `/games`。
2. 选择官方规则，例如经典 8 人局、社交 8 人局或 12 人预女猎白局。
3. 页面根据规则人数生成座位。
4. 用户点击一个座位。
5. 右侧或下方展示可选虚拟玩家列表。
6. 用户选择虚拟玩家，座位立即显示该玩家头像和名称。
7. 用户继续安排其他座位。
8. 阵容预览显示已选人数、空席、模型分布和关键提示。
9. 用户点击“发起对局”。
10. 前端提交 `player_configs`，后端冻结快照并进入直播页。

### 玩家库为空

如果没有虚拟玩家：

- 座位区仍显示所有空席。
- 选择区展示空状态。
- 主操作为“去玩家库创建”。
- 返回 `/games` 后自动读取新创建的玩家。

### 玩家库读取失败

如果玩家库读取失败：

- 对局仍允许发起，使用随机默认玩家。
- 座位选人区显示错误提示。
- 提供“重试读取玩家库”。
- 不阻塞规则选择、随机种子、最大轮数和发起对局。

## 页面结构

建议把 `/games` 创建区组织成三个层次。

### 顶部控制台

保留当前内容：

- 对局大厅标题。
- 随机种子。
- 最大轮数。
- 演示慢速。
- 发起对局按钮。

优化点：

- 发起按钮旁展示“已安排 X / N 名玩家”。
- 如果有空席，提示“空席将由系统随机补齐”。
- 如果玩家库读取失败，提示“无法读取玩家库，本局可继续使用随机玩家”。

### 官方规则区

保留现有规则卡片和规则详情。

优化点：

- 规则切换时保留前 N 个座位配置。
- 从 12 人切回 8 人时，丢弃 9 到 12 号座位配置前给出轻量提示。
- 规则详情中增加“座位人数”和“建议配置完整度”的提示。

### 选人组局台

这是本轮重点。

布局建议：

```text
┌────────────────────────────────────────────────────────────┐
│ 阵容预览：已选 5/8 · 空席 3 · 收藏玩家 2 · 模型 3 种         │
├──────────────────────────────┬─────────────────────────────┤
│ 座位模块                     │ 玩家选择                    │
│ 1号 2号 3号 4号              │ 搜索 / 标签 / 收藏           │
│ 5号 6号 7号 8号              │ 玩家卡片列表                 │
│                              │ 清空 / 随机填充 / 去玩家库    │
└──────────────────────────────┴─────────────────────────────┘
```

移动端：

- 先显示阵容预览。
- 再显示座位模块。
- 选中座位后展开玩家选择抽屉或纵向列表。
- 发起按钮保持在顶部控制台，不做固定悬浮。

## 交互设计

### 座位状态

每个座位至少有四种状态：

- 空席：没有选择玩家。
- 已选：已经确认虚拟玩家。
- 当前座位：用户正在操作。
- 异常：引用的玩家不存在或已从玩家库删除。

展示内容：

- 座位号。
- 玩家头像或空席轮廓。
- 玩家名称。
- 模型短标签。
- 性格或策略短标签。

空席不代表无法开局。后端仍会随机补齐缺失座位。

### 选择玩家

点击玩家卡片后，建议直接应用到当前座位，不再要求额外点击“确认选择”。当前代码已有 pending selection 和确认按钮，但实际组局体验里会显得多一步。

如果担心误点，可以提供撤销或“清空当前座位”，而不是强制二次确认。

推荐行为：

- 点击玩家卡片：立即填入当前座位。
- 点击已选座位：右侧高亮当前玩家。
- 点击同一个玩家卡：保持选中。
- 点击“清空座位”：移除当前座位的 `profile_id` 和临时覆盖。
- 点击“随机填充空席”：从玩家库中随机选择未使用玩家填入空席。

### 重复选择

第一版建议默认不允许同一个虚拟玩家同时占多个座位。

原因：

- 更符合“组一桌不同玩家”的直觉。
- 避免直播和复盘里出现多个同名同头像玩家。
- 减少用户误操作。

如果用户确实想复用同一档案，应先在 `/players` 复制玩家，再回到大厅选择副本。

交互规则：

- 已被其他座位占用的玩家卡片显示“已在 X 号位”。
- 用户仍可点击，但系统提示需要先清空原座位。
- 后续版本可以增加“允许重复使用”开关，本轮不做。

### 筛选与排序

玩家选择区应支持轻量筛选：

- 搜索昵称、标签、模型、简介。
- 只看收藏。
- 按模型筛选。
- 按性格筛选。
- 按策略筛选。

排序建议：

1. 收藏玩家优先。
2. 未被占用玩家优先。
3. 最近更新优先。

这些筛选逻辑可以复用玩家库卡片已有思路，但不直接复用完整 `VirtualPlayerLibrary`，避免把编辑功能带进创建对局页。

### 快速操作

第一版建议实现：

- 清空当前座位。
- 清空全部座位。
- 随机填充空席。
- 只用收藏玩家填充。
- 跳转玩家库创建新玩家。

暂不实现：

- 保存阵容模板。
- 拖拽换座。
- 批量按模型覆盖。

## 阵容预览

新增 `LineupSummary` 或内联摘要模块。

展示内容：

- 已安排人数：`已选 5 / 8`。
- 空席数量：`空席将随机补齐`。
- 重复/异常提示。
- 模型分布，例如 `DeepSeek 4 人 · Qwen 2 人`。
- 性格分布，例如 `均衡 3 · 谨慎 2 · 进攻 1`。
- 收藏玩家数量。

如果没有选择任何玩家，文案应强调“可以直接开局，系统会随机补齐玩家”，避免用户误以为必须配置完才能开始。

## 数据规则

### 前端状态

继续使用现有 `PlayerConfig[]`：

```ts
type PlayerConfig = {
  seat: number;
  profile_id?: string;
  model?: string;
  personality_id?: string;
  appearance_id?: string;
};
```

本轮不新增字段。

### 规范化规则

提交前继续执行：

- 丢弃超出当前规则人数的座位。
- 删除已经不存在的 `profile_id`。
- 去除空白模型覆盖。
- 只提交有实际配置的座位。
- 按座位号排序。

新增前端约束：

- 默认阻止重复 `profile_id`。
- 随机填充时只选择未占用玩家。
- 玩家库读取失败时不改写已有座位配置，但提交前会清理无效引用。

### 后端规则

第一阶段后端不需要新增字段，但建议补充测试确认：

- 部分座位配置仍能开局。
- `profile_id` 不存在时返回 422 或被当前规范化逻辑拒绝。
- 同一 `profile_id` 重复使用第一阶段由前端阻止；后端保持现状，不作为本轮阻塞项。

后续如果需要更强一致性，再由后端补充重复 `profile_id` 校验。本轮先避免扩展 API 和数据库逻辑。

## 组件设计

建议拆分 `PlayerConfigPanel`，避免继续变大。

### `PlayerConfigPanel`

职责：

- 管理选中座位。
- 接收 `configs`、`profiles` 和 `onChange`。
- 组合子组件。

不直接负责复杂筛选和摘要计算。

### `SeatGrid`

职责：

- 渲染规则人数对应的座位。
- 展示空席、已选、当前、异常状态。
- 处理座位点击。

输入：

- `playerCount`
- `configs`
- `profiles`
- `selectedSeat`
- `onSelectSeat`

### `SeatDetailPanel`

职责：

- 展示当前座位详情。
- 提供清空当前座位、模型覆盖等操作。
- 展示已选玩家完整摘要。

### `ProfilePicker`

职责：

- 渲染可选玩家卡片。
- 搜索、筛选、排序。
- 标记已占用玩家。
- 点击玩家后应用到当前座位。

### `LineupSummary`

职责：

- 统计已选人数、空席、模型分布、性格分布。
- 展示开局前风险或提示。

### `lineupUtils.ts`

建议新增纯函数文件：

- `applyProfileToSeat(configs, seat, profileId)`
- `clearSeat(configs, seat)`
- `clearAllSeats()`
- `randomFillEmptySeats(configs, profiles, playerCount, options)`
- `findDuplicateProfileSelections(configs)`
- `summarizeLineup(configs, profiles, playerCount)`
- `removeInvalidProfileRefs(configs, validProfileIds)`

这些函数应有独立测试，减少 UI 测试负担。

## 样式方向

继续沿用暗夜哥特视觉，不新增大型视觉资产。

重点打磨：

- 座位卡固定尺寸，避免名字长短造成布局跳动。
- 已选座位使用金色描边和头像高亮。
- 当前座位使用更明显的内发光或角标。
- 空席保持轮廓感，不要像错误状态。
- 玩家卡片使用半身图/头像作为主视觉。
- 筛选区保持紧凑，不做厚重后台表格。

不要做：

- 大面积营销式说明。
- 页面级嵌套卡片。
- 过度装饰的渐变背景。
- 让按钮文字在窄屏溢出。

## 风险与处理

### 组件复杂度继续上升

处理：

- 强制拆分 `SeatGrid`、`ProfilePicker`、`LineupSummary`。
- 复杂状态转换放到 `lineupUtils.ts`。

### 规则切换导致座位配置丢失

处理：

- 保留前 N 个座位。
- 丢弃超出人数的座位。
- 摘要区显示轻量提示。

### 用户误以为空席不能开局

处理：

- 文案明确“空席将随机补齐”。
- 发起按钮不因空席禁用。

### 玩家库读取失败阻塞开局

处理：

- 读取失败只影响选人。
- 创建对局仍可使用随机默认玩家。

### 重复玩家策略前后端不完全一致

处理：

- 第一版前端默认不允许重复。
- 后端保持现状，不作为本轮阻塞项。
- 第二阶段再评估是否补充后端重复校验。

## 成功标准

- 用户能在 `/games` 清楚完成一桌玩家的选择。
- `/players` 创建出来的玩家能自然进入 `/games` 选人流程。
- 选择、替换、清空、随机填充都直观可用。
- 空席、加载失败、玩家库为空都有清晰提示。
- 发起对局 payload 稳定正确，不破坏现有开局流程。
- 页面在桌面和移动端都不拥挤、不溢出。
- 后续增加阵容模板时，可以复用当前 `lineupUtils` 和阵容摘要结构。
