# Live V2 渐进式重构准则

状态：V1 已于 2026-08-20 整包退场；对局代码目录现为 `apps/api/app/match/`。本文件仍约束 Live V2 的开发门禁与直播/复播边界，不是一份待执行的退场计划。

## 1. 目标

从零建立一套只服务于直播的展示与播放系统，解决当前直播中画面、字幕、语音和玩家切换分别由不同状态推进的问题。

Live V2 最初按最小环节重构；在 2026-07-23 用户明确批准“开发完整对局”后，当前工作包调整为完成整局，但包内每个动作仍必须满足以下条件：

- 行为可独立观察。
- 输入和结束条件明确。
- 画面、字幕、语音和状态转换一致。
- 自动化验证通过。
- 每个动作都留下可单独验证的证据；整局完成后统一交付用户观察。

## 2. 最高优先级门禁

以下规则高于开发效率、代码复用和一次性完整度：

1. 默认一次只开发一个最小环节；用户在看过完整范围、状态、隐私和验收计划后，可以明确批准把多个已经定义清楚的环节合并为一个扩大验收包。
2. 开发前必须写清本环节的范围、非范围和验收标准。
3. 用户没有明确回复“通过”或“进入下一步”，不得开发下一环节。
4. 用户验收未通过时，只修复当前环节，不顺手修改相邻功能。
5. 不提前铺设尚未批准的业务能力；确需预留时，只允许定义稳定接口，不实现后续行为。
6. 每一步都必须保留可回滚边界。
7. “验收通过”和“提交代码”是两个独立授权；未经用户明确要求，不执行 Git 提交或推送。
8. Live V2 的直播动作、展示、字幕、语音、时钟和记录业务代码必须重新编写，不得为了提速复用、包装、复制或改名迁移任何旧直播业务实现；这条规则不得扩大解释为重做大厅、规则目录、玩家库等非直播产品模块。
9. 运行时流程必须由冻结规则、角色能力和当前游戏状态动态生成，不得把“狼人、守卫、预言家、女巫”等角色名称或固定先后顺序写进阶段主执行器。
10. 当前完整对局工作包已经得到用户明确授权，不再在首夜、首日、投票或下一轮之间设置人工开发停点；只有失败时停止运行，成功时持续推进到确定性胜负。

## 3. 重构边界

### 3.1 必须新建

- 独立的 Live V2 页面、路由和目录。
- 独立的直播协议和类型。
- 独立的直播展示状态机。
- 独立的实时字幕状态。
- 独立的实时语音播放状态。
- 必要时新增后端直播编排层，但不把它塞回旧直播页面的兼容逻辑。

### 3.2 禁止继承的旧逻辑

Live V2 不得导入、复用、包装、复制或改名迁移以下旧业务实现：

- 旧 `liveDirector` 的自动推进和等待逻辑。
- 旧直播语音队列的 ACK、超时、补播和抢占逻辑。
- Replay 的播放游标、音频时钟和 `holdAdvance`。
- `session_timeline` 的历史折叠结果作为直播播放队列。
- 通过“再加一个布尔状态或定时器”修补旧直播行为。
- 旧游戏规则编排、模型调用、provider、streaming 和 speech gate。
- 旧 TTS 客户端封装、materializer、voice stream 和 speech delivery。
- 旧对局记录、事件记录、语音记录和持久化 repository。
- 旧 Live、Replay、对局页面中的领域类型、状态 hook、UI 组件和请求封装。

### 3.3 只允许共享基础设施

以下内容属于运行基础设施，不视为旧业务代码复用，可以共享：

- Python、TypeScript、React、FastAPI、SQLAlchemy 等语言、框架和标准库。
- 官方或第三方模型、TTS、数据库和音频 SDK；V2 必须基于 SDK 编写自己的适配层，不能调用旧适配层。
- 数据库 engine/session、日志、指标、trace、进程生命周期和通用鉴权中间件。
- 密钥、Endpoint、模型 ID、采样率等配置值；不得共享含旧业务推进语义的配置对象。
- V2 自己创建并已经通过用户验收的 V2 代码。

除此之外默认全部禁止。确需共享新的非业务基础设施时，必须在开发前列出具体模块、证明其不包含旧游戏、直播、Replay、模型或语音业务语义，并取得用户明确批准；未获批准不得导入。

### 3.4 保留现有上游产品模块

本次项目目标是重做直播页及其直播运行链路，不是重做整个产品。以下现有模块保持原位，不得因为 Live V2 另建一套替代实现：

- 现有移动端对局大厅及其规则选择、玩家选择、阵容质量预检和交互 UI。
- 现有规则目录、玩家资料库和大厅所需的查询接口。
- 与直播展示无关的全局导航和产品外壳。

现有大厅可以通过明确的 V2 创建 DTO 把已经完成预检的最终配置交给 V2，并在创建成功后跳转 Live V2。这个集成方向是“现有大厅调用 V2 边界”，不得反向让 V2 导入旧大厅组件、状态或请求实现，也不得复制一套 V2 大厅。

创建 V2 对局只冻结规则、玩家、身份和能力快照，状态必须保持 `waiting_to_start`，不得视为正式开局。普通直播或上帝视角中，首个用户点击实时观赛并完成音频解锁后发送的受众 ready 才能原子写入 `game_started`、填写 `run.started_at` 并启动法官流程；读取页面和快照不得产生任何模型或 TTS 请求。

必须增加并持续保留导入边界测试，至少保证：

- `app/match/`（HTTP 仍为 `/api/v2`）不导入 `app.werewolf` 或旧包名 `app.v2`。
- Mobile `src/match/` 不导入旧 Live、Replay、游戏状态和播放模块。
- Admin `src/match/` 不导入旧对局记录的 parser、types、API 或页面组件。
- 复制旧实现到 match 目录同样视为违规，不能通过路径改名绕过边界测试。

攻击结算常量属于规则目录，放在 `app.rule_sets.types`，V2 可以从这里读取。TTS 适配层必须由 V2 自己编写：`app/match/tts_client.py` 自行构造 session 请求，不得调用 `app.shared.volcengine_tts`。

2026-07-28 与 07-30 曾引入两处违规，2026-08-20 已按上述方式修复。边界测试必须保持绿色。

## 4. 直播与复播完全分离

### 4.1 Live V2

- 直播页面进入时读取一份“当前直播快照”。
- 快照之后只消费现在和未来发生的直播事件。
- 不补播进入页面前的字幕和语音。
- 断线重连后直接跳到服务器当前直播状态。
- 断线期间错过的历史语音不得进入播放队列。
- 直播状态由服务器的当前展示序列决定，不由客户端追赶数据库历史决定。

### 4.2 Replay

- Replay 使用完整持久化时间线。
- Replay 拥有自己的播放游标、暂停、倍速、拖动和音频时钟。
- Replay 可以重建过去，Live V2 不可以。
- 两者不得共享业务组件、状态机、协议类型、请求封装或推进逻辑；只能各自建立在第 3.3 节允许的运行基础设施上。

## 5. 唯一直播时序

服务器必须为所有可展示内容提供唯一且单调递增的 `presentation_seq`。

每个展示单元至少需要明确：

- `presentation_seq`
- `presentation_id`
- `phase_id`
- `actor_id` 或裁判标识
- `speech_id`，仅发言类内容需要
- `segment_index`，仅分段发言需要
- `source_event_id`
- `state` 或明确的事件类型

必须满足以下不变量：

1. 任意时刻最多只有一个 `active_speaker`。
2. 同一发言的 `segment_index` 只能递增，不能回退。
3. 字幕和语音必须引用同一个 `presentation_id`、`speech_id` 和分段序号。
4. A 玩家没有正式结束前，不得公开切换到 B 玩家。
5. 一旦 B 玩家被激活，任何迟到的 A 玩家字幕、语音或状态都必须拒绝或丢弃，不能重新激活 A。
6. 重复事件必须幂等，不得导致重复字幕、重复语音或重复状态转换。
7. 未知、越序或缺少关键标识的事件必须失败关闭，不能靠猜测继续播放。

## 6. 发言、语音与保存准则

公开发言使用一条明确的生命周期：

`speech_opened -> segment_committed* -> speech_sealed -> audio_drained_or_failed -> speech_closed`

具体规则：

1. 模型可以流式生成。
2. 模型流结束后，只要得到非空自然文本即可成为 `segment_committed`；不得限制句数、句末标点、字符长短、引号、Markdown 或换行。
3. 法官和玩家都必须保留模型生成的完整发言并交给 TTS，不得截取第一句或因为表达格式拒绝动作。
4. 只有响应无法解析、缺少动作必需字段、发言为空、目标违反确定性规则或发生真实模型故障时才能拒绝动作；其他表达质量只能记录非阻塞观测，不能让游戏失败。
5. 法官的模型和 TTS 音色必须在每次法官动作开始时读取法官配置；动作规格、模型客户端默认值和 TTS 客户端默认值都不得覆盖法官配置。实际使用的配置版本、模型和音色必须写入动作证据。
6. `speech_sealed` 之后不得再接受新的文本或语音分段。对局决策在此时落盘；引擎可以立刻激活下一位模型请求。
7. 当前发言的所有已接受语音必须播放完成，或者进入明确的终止失败状态，才能 `speech_closed`。`audio_drained` / `speech_closed` 只推进 `playback_cursor`，不再阻塞对局。
8. 下一位模型请求的唯一门闩是上一动作已经 `speech_sealed`（或 silent decision 已提交）。不得等待 TTS、官方时钟或 `speech_closed`。
9. TTS 失败只失败该条播放（`presentation_failed`，cursor 仍前进），不得回写对局失败、不得回滚夜晚或放逐。
10. 单个观众的播放 ACK 只能用于遥测或本地资源释放，不能控制整局直播和其他观众的游戏推进。
11. 每个公开语音分段都必须保存为全新的 V2 语音资产，不复用旧语音表、旧语音任务或旧文件命名空间。
12. TTS 产生的同一份有序 PCM 必须同时交给实时广播和 V2 语音保存器，禁止为保存再次请求 TTS，也禁止直播改为读取保存文件。
13. 保存完成必须校验 sample 数、时长和 PCM 哈希；保存资产与实际广播源不一致时，本次动作不得成功。
14. 保存失败必须产生明确的 `recording` 失败并停止当前动作，不能留下“对局成功但语音缺失”的记录。
15. 保存语音供 Admin V2 对局记录和未来独立 Replay 使用，但不得出现在普通 Live snapshot 中，也不得成为直播补播或重连队列。

## 7. 画面与字幕准则

- 当前画面只能由当前 `presentation_seq` 派生。
- 当前玩家、字幕和正在播放的语音必须指向同一展示单元。
- 切换玩家时必须原子更新当前玩家、字幕容器和语音归属。
- 不得使用多个互不相关的 cursor 分别决定画面和语音。
- 字幕不得在语音结束后回退到上一句。
- 语音尚未开始时，不得因为未来事件提前展示下一位玩家正在发言。
- 非发言状态必须使用明确的裁判、等待或行动展示，不得沿用上一位玩家的发言状态。

## 8. 隐私准则

- 普通直播和上帝视角必须使用不同的服务端投影。
- 前端不得先接收完整秘密事件再自行隐藏。
- 狼队身份、狼刀目标、神职选择和查验结果必须默认失败关闭。
- 每新增一个细小环节，都必须分别验证普通直播和上帝视角能看到什么。
- 隐私验证未通过时，该环节不得进入用户验收。

## 9. 故障和超时准则

每个等待都必须有唯一责任方、明确起点、明确终点和可观测原因。

禁止：

- 用多个定时器竞争决定同一个状态。
- 用播放超时模拟正常完成。
- 超时后把旧语音重新插入当前队列。
- 因为语音失败而回退画面序列。
- 客户端断线导致全局游戏永久阻塞。

每个失败必须归类为模型响应不可用、规则目标非法、TTS、录音保存、传输、播放或状态协议失败，不能统一显示为“等待中”。自然语言风格、句数、标点、长度、引号、Markdown 或换行不得成为失败类别。

### 9.1 管理员打断整局

- “打断整局”只属于 Admin 运营控制面，不向普通 Mobile 玩家提供。
- 控制请求使用既有 `runs.control` 权限、CSRF、`Idempotency-Key`、二次确认、操作原因和审计。
- V2 运行独立持久化 `stop_requested_at`；停止请求必须在新的模型请求前、模型流块之间、TTS 帧之间和展示关闭前被检查。
- 管理员打断使用独立的 `canceled` 终态和 `game_canceled` 事实，不得伪装成 `failed`、timeout、无发言或正常完成。
- 当前活动展示进入 `canceled`，尚在写入的语音资产进入 `canceled`；已经完整保存的语音资产可以保留，但 Live 不得继续播放或补播。
- 普通直播和上帝视角只接收相同的 `operator_interrupted` 安全终止码，不接收管理员身份、操作原因或任何私密行动内容。
- Mobile 收到 `canceled` 后必须立即停止当前 PCM、清空活动展示并关闭实时连接；历史记录仍由独立的 V2 事实序列保存，不能借 Replay 游标恢复直播播放。

## 10. 最小开发单元

默认开发单元必须能用一句话描述，并且只产生一个新的可观察结果。例如：

- “Live V2 能展示当前对局的玩家座位快照。”
- “Live V2 能实时展示一条裁判字幕。”
- “Live V2 能播放一条裁判语音并在结束后进入空闲状态。”
- “狼人睁眼提示能在上帝视角出现，普通直播只显示夜晚等待。”

以下描述默认过大，未经过展开设计和用户明确批准时，不允许作为单次开发范围：

- “完成首夜。”
- “完成狼刀。”
- “完成神职功能。”
- “完成直播语音。”
- “完成断线恢复。”

当前“完成整局”已经获得明确批准，因此不受上述默认切片大小限制；该授权只覆盖 Live V2 整局运行链路，不扩大为重做大厅、规则目录、玩家库或 Replay。

用户可以明确批准扩大验收包，但必须同时满足：

- 包内每个动作、能力激活、状态转换和失败停止点都已经单独定义。
- 普通直播、上帝视角和未来玩家视角的投影边界已经逐项列明。
- 扩大范围不能减少持久化证据、不变量测试或真实对局观察项。
- 运行时仍按严格的动作和展示生命周期逐项执行，不能把扩大验收理解为跳过中间状态。
- 批准只对本次写明的范围生效，不自动授权相邻阶段、其他规则或其他角色。

## 11. 每一步的执行流程

### 11.1 开发前

必须先向用户提交：

- 本步唯一目标。
- 明确不做的内容。
- 将修改的模块。
- 事件输入与状态转换。
- 普通直播和上帝视角的预期表现。
- 画面、字幕、语音和结束条件。
- 自动化验证计划。
- 用户观察清单。

用户确认范围后才能实现。

### 11.2 实现后

必须提供：

- 实际修改文件。
- 自动化测试和结果。
- 一个真实的 `run_id`。
- 关键事件 ID 或展示序列。
- 用户需要观察的具体时间点和预期结果。
- 已知限制。

然后停止开发，等待用户本人观察。

### 11.3 用户验收后

- 用户未通过：继续当前环节，不能进入下一步。
- 用户通过：冻结当前契约和回归测试。
- 用户明确要求提交：创建只包含当前环节的本地提交，不推送。
- 用户明确允许下一步：再提出下一步的范围和验收标准。

本节是默认流程。当前完整对局工作包以整局终态作为一次验收边界，不在夜晚、白天、警长竞选、发言、平票 PK、放逐或死亡响应之间等待人工批准。

## 12. 建议开发顺序

### 12.1 直播底座

以下每一项都是独立验收环节：

1. Live V2 独立路由和空页面。
2. 当前对局快照。
3. 只接收快照之后的新事件。
4. `presentation_seq` 去重和越序拒绝。
5. 单一当前展示单元。
6. 单条裁判字幕。
7. 单条裁判语音。
8. 字幕与语音引用同一个展示单元。
9. 展示单元明确结束并回到空闲。
10. 断线重连跳到当前快照且不补播旧语音。
11. 普通直播与上帝视角投影隔离。

底座没有全部通过前，不进入正式游戏阶段开发。

### 12.2 游戏开场

每一项单独验收：

1. 对局开始状态。
2. 玩家座位确认。
3. 角色和规则快照加载。
4. 裁判开场字幕。
5. 裁判开场语音。
6. 开场展示关闭。
7. 进入首夜的唯一状态转换。

### 12.3 能力运行时底座

首夜不是固定角色列表。进入首夜前必须先独立验收以下运行时能力：

1. 从现有大厅交付的冻结规则和身份快照编译 V2 能力快照。
2. 能力版本、行动主体、激活窗口、依赖关系和结算处理器完整校验。
3. 未知能力、未知版本、循环依赖或缺失隐私投影时失败关闭。
4. 根据当前状态发现可激活的个人、阵营、系统或事件响应能力。
5. 为每次能力激活生成稳定、幂等的 `activation_id`。
6. 展示顺序与知识依赖相互独立；展示靠后不能自动看到更早的秘密结果。
7. 每次需要选择或发言的激活使用独立 ActionContext 和真实模型请求。
8. 模型结果通过能力自己的结构和合法目标策略确定性验证。
9. 决策只生成效果意图，不允许模型直接修改玩家、阶段、身份或胜负状态。
10. 普通直播、上帝视角和未来玩家视角分别由服务端失败关闭投影。
11. 当前激活完整封口后，规划器才能选择下一个可运行激活。
12. 没有未完成的阻塞激活和新触发的响应能力时，当前行动窗口才能关闭。

### 12.4 角色能力验收

角色只是一个或多个版本化能力的载体，不能成为主执行器分支。每种能力至少验证：

1. 能力实例归属和使用次数。
2. 激活条件、跳过条件和阻塞属性。
3. 行动者能看到的知识投影。
4. 模型请求、结构化选择和私密发言。
5. 合法目标、资源消耗和跨轮限制。
6. 效果意图持久化。
7. 与其他效果的确定性结算关系。
8. 普通直播的安全进度投影。
9. 上帝视角的完整结果投影。
10. 私密字幕、语音和语音资产的受众隔离。
11. 激活失败时停在当前能力，不生成静态、随机或旧逻辑兜底。
12. 激活完成后由规划器重新计算后续能力，而不是跳到写死的下一个角色。

狼人共同袭击、守护、查验、救人、毒人和死亡响应等分别作为能力验收。用户明确批准时，可以把已经完整定义的多项能力合并到一个扩大验收包，但每项证据和测试仍须保留。

### 12.5 夜间效果结算与窗口关闭

能力激活完成后逐项验收：

1. 夜间效果意图汇总。
2. 攻击、防护、治疗、额外伤害、阻断和其他已注册效果的确定性结算。
3. 结算事件继续触发符合规则的响应能力。
4. 响应能力执行后重新结算，直到没有新的阻塞激活。
5. 死亡、存活、资源和私密知识结果原子落库。
6. 天亮提示。
7. 按冻结规则决定公开平安夜、死亡名单或其他公开结果。
8. 公告字幕和语音。
9. 玩家公开状态画面更新。
10. 当前夜间行动窗口封口。
11. 进入冻结规则声明的下一个行动窗口，而不是固定跳转到某个角色或页面状态。

## 13. 回归保护

每通过一个环节，都必须新增并保留对应不变量测试。至少覆盖：

- 序列单调递增。
- 重复事件幂等。
- 越序事件被拒绝。
- 同时最多一个当前玩家。
- A 未关闭时 B 不可激活。
- B 激活后迟到的 A 不可恢复。
- 字幕和语音属于同一分段。
- 保存语音和直播广播使用同一份 PCM、sample 数和校验值。
- 语音资产未保存完成时动作不可成功，保存失败明确停止。
- TTS 失败只推进一次。
- 重连不补播历史语音。
- 普通直播不包含秘密信息。

已经验收通过的行为不得在后续步骤中悄悄改写；如确需修改，必须重新说明影响并再次获得用户批准。

## 14. 每个新任务的开场模板

新任务必须先读取本文档。当前授权状态见第 1 节、第 2.10 条和第 10 节末尾：**“完成整局”已于 2026-07-23 获得明确批准**，整局运行链路内的动作不再逐个设置人工开发停点。该授权只覆盖 Live V2 整局链路，不包含大厅、规则目录、玩家库和 Replay。

建议使用以下指令：

> 阅读 `docs/live-v2-refactor-guidelines.md`，严格按照门禁执行。当前“完成整局”已获批准，整局链路内的动作不需要逐个等待我批准停点；超出整局链路的范围（大厅、规则目录、玩家库、Replay）仍必须先单独获批。先核对现有代码与实际运行路径，然后提出本步范围、非范围、状态转换、自动化验证和人工观察清单。在我明确批准范围前不要修改代码；实现完成后提供真实 run_id 并停止，等待我本人观察。不要修改旧直播页面来兼容 Live V2，不要提交或推送代码，除非我明确要求。

如果任务本身就是要扩大范围（例如开发 Replay 或改动大厅），不要套用上面的模板，改为先按第 10 节提交扩大验收包的说明并等待批准。

每个新任务还必须执行 V2 旧业务零复用检查：不得导入、包装、复制或改名迁移旧游戏、模型、TTS、Live、Replay、记录或 UI 业务代码，只能使用第 3.3 节列出的运行基础设施。

## 15. 完成定义

单个环节只有同时满足以下条件才算完成：

- 代码范围符合批准内容。
- 自动化验证通过。
- 真实对局证据完整。
- 涉及公开语音时，对应 V2 语音资产已经保存并通过同源 PCM 校验。
- 画面、字幕、语音、时序和隐私均符合预期。
- 用户本人明确表示通过。

Live V2 只有在整局所有动作分别具备证据、普通/上帝投影边界通过测试、真实模型与同源语音完整跑到确定性胜负后才算完成；仅“流程没有报错”不算完成标准。
