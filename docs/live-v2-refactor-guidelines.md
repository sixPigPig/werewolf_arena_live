# Live V2 渐进式重构准则

## 1. 目标

从零建立一套只服务于直播的展示与播放系统，解决当前直播中画面、字幕、语音和玩家切换分别由不同状态推进的问题。

本次重构追求的不是一次性完成整局狼人杀，而是让每一个最小环节都满足以下条件：

- 行为可独立观察。
- 输入和结束条件明确。
- 画面、字幕、语音和状态转换一致。
- 自动化验证通过。
- 用户本人观察并明确同意后，才允许开发下一环节。

## 2. 最高优先级门禁

以下规则高于开发效率、代码复用和一次性完整度：

1. 一次只开发一个最小环节。
2. 开发前必须写清本环节的范围、非范围和验收标准。
3. 用户没有明确回复“通过”或“进入下一步”，不得开发下一环节。
4. 用户验收未通过时，只修复当前环节，不顺手修改相邻功能。
5. 不提前铺设尚未批准的业务能力；确需预留时，只允许定义稳定接口，不实现后续行为。
6. 每一步都必须保留可回滚边界。
7. “验收通过”和“提交代码”是两个独立授权；未经用户明确要求，不执行 Git 提交或推送。
8. Live V2 的直播动作、展示、字幕、语音、时钟和记录业务代码必须重新编写，不得为了提速复用、包装、复制或改名迁移任何旧直播业务实现；这条规则不得扩大解释为重做大厅、规则目录、玩家库等非直播产品模块。

## 3. 重构边界

### 3.1 必须新建

- 独立的 Live V2 页面、路由和目录。
- 独立的直播协议和类型。
- 独立的直播展示状态机。
- 独立的实时字幕状态。
- 独立的实时语音播放状态。
- 必要时新增后端直播编排层，但不把它塞回旧直播页面的兼容逻辑。

### 3.2 禁止继承的旧逻辑

Live V2 不得导入、复用、包装、复制或改名迁移以下旧业务实现：

- 旧 `liveDirector` 的自动推进和等待逻辑。
- 旧直播语音队列的 ACK、超时、补播和抢占逻辑。
- Replay 的播放游标、音频时钟和 `holdAdvance`。
- `session_timeline` 的历史折叠结果作为直播播放队列。
- 通过“再加一个布尔状态或定时器”修补旧直播行为。
- 旧游戏规则编排、模型调用、provider、streaming 和 speech gate。
- 旧 TTS 客户端封装、materializer、voice stream 和 speech delivery。
- 旧对局记录、事件记录、语音记录和持久化 repository。
- 旧 Live、Replay、对局页面中的领域类型、状态 hook、UI 组件和请求封装。

### 3.3 只允许共享基础设施

以下内容属于运行基础设施，不视为旧业务代码复用，可以共享：

- Python、TypeScript、React、FastAPI、SQLAlchemy 等语言、框架和标准库。
- 官方或第三方模型、TTS、数据库和音频 SDK；V2 必须基于 SDK 编写自己的适配层，不能调用旧适配层。
- 数据库 engine/session、日志、指标、trace、进程生命周期和通用鉴权中间件。
- 密钥、Endpoint、模型 ID、采样率等配置值；不得共享含旧业务推进语义的配置对象。
- V2 自己创建并已经通过用户验收的 V2 代码。

除此之外默认全部禁止。确需共享新的非业务基础设施时，必须在开发前列出具体模块、证明其不包含旧游戏、直播、Replay、模型或语音业务语义，并取得用户明确批准；未获批准不得导入。

### 3.4 保留现有上游产品模块

本次项目目标是重做直播页及其直播运行链路，不是重做整个产品。以下现有模块保持原位，不得因为 Live V2 另建一套替代实现：

- 现有移动端对局大厅及其规则选择、玩家选择、阵容质量预检和交互 UI。
- 现有规则目录、玩家资料库和大厅所需的查询接口。
- 与直播展示无关的全局导航和产品外壳。

现有大厅可以通过明确的 V2 创建 DTO 把已经完成预检的最终配置交给 V2，并在创建成功后跳转 Live V2。这个集成方向是“现有大厅调用 V2 边界”，不得反向让 V2 导入旧大厅组件、状态或请求实现，也不得复制一套 V2 大厅。

必须增加并持续保留导入边界测试，至少保证：

- API V2 不导入 `app.werewolf` 下的旧业务模块。
- Mobile V2 不导入旧 Live、Replay、游戏状态和播放模块。
- Admin V2 不导入旧对局记录的 parser、types、API 或页面组件。
- 复制旧实现到 V2 目录同样视为违规，不能通过路径改名绕过边界测试。

## 4. 直播与复播完全分离

### 4.1 Live V2

- 直播页面进入时读取一份“当前直播快照”。
- 快照之后只消费现在和未来发生的直播事件。
- 不补播进入页面前的字幕和语音。
- 断线重连后直接跳到服务器当前直播状态。
- 断线期间错过的历史语音不得进入播放队列。
- 直播状态由服务器的当前展示序列决定，不由客户端追赶数据库历史决定。

### 4.2 Replay

- Replay 使用完整持久化时间线。
- Replay 拥有自己的播放游标、暂停、倍速、拖动和音频时钟。
- Replay 可以重建过去，Live V2 不可以。
- 两者不得共享业务组件、状态机、协议类型、请求封装或推进逻辑；只能各自建立在第 3.3 节允许的运行基础设施上。

## 5. 唯一直播时序

服务器必须为所有可展示内容提供唯一且单调递增的 `presentation_seq`。

每个展示单元至少需要明确：

- `presentation_seq`
- `presentation_id`
- `phase_id`
- `actor_id` 或裁判标识
- `speech_id`，仅发言类内容需要
- `segment_index`，仅分段发言需要
- `source_event_id`
- `state` 或明确的事件类型

必须满足以下不变量：

1. 任意时刻最多只有一个 `active_speaker`。
2. 同一发言的 `segment_index` 只能递增，不能回退。
3. 字幕和语音必须引用同一个 `presentation_id`、`speech_id` 和分段序号。
4. A 玩家没有正式结束前，不得公开切换到 B 玩家。
5. 一旦 B 玩家被激活，任何迟到的 A 玩家字幕、语音或状态都必须拒绝或丢弃，不能重新激活 A。
6. 重复事件必须幂等，不得导致重复字幕、重复语音或重复状态转换。
7. 未知、越序或缺少关键标识的事件必须失败关闭，不能靠猜测继续播放。

## 6. 发言、语音与保存准则

公开发言使用一条明确的生命周期：

`speech_opened -> segment_committed* -> speech_sealed -> audio_drained_or_failed -> speech_closed`

具体规则：

1. 模型可以流式生成。
2. 只有到达完整句子边界并通过硬性质量检查的文本，才能成为 `segment_committed`。
3. 完整且已接受的句子可以在模型尚未完全返回时开始生成 TTS。
4. 模型未结束时，当前发言不得被视为封口。
5. `speech_sealed` 之后不得再接受新的文本或语音分段。
6. 当前发言的所有已接受语音必须播放完成，或者进入明确的终止失败状态，才能 `speech_closed`。
7. 只有 `speech_closed` 后才能激活下一位玩家。
8. TTS 失败必须产生明确的失败事件并停止当前动作，不能伪装成功、生成旧语音兜底或等待隐式超时后悄悄推进。
9. 单个观众的播放 ACK 只能用于遥测或本地资源释放，不能控制整局直播和其他观众的游戏推进。
10. 每个公开语音分段都必须保存为全新的 V2 语音资产，不复用旧语音表、旧语音任务或旧文件命名空间。
11. TTS 产生的同一份有序 PCM 必须同时交给实时广播和 V2 语音保存器，禁止为保存再次请求 TTS，也禁止直播改为读取保存文件。
12. 保存完成必须校验 sample 数、时长和 PCM 哈希；保存资产与实际广播源不一致时，本次动作不得成功。
13. 保存失败必须产生明确的 `recording` 失败并停止当前动作，不能留下“对局成功但语音缺失”的记录。
14. 保存语音供 Admin V2 对局记录和未来独立 Replay 使用，但不得出现在普通 Live snapshot 中，也不得成为直播补播或重连队列。

## 7. 画面与字幕准则

- 当前画面只能由当前 `presentation_seq` 派生。
- 当前玩家、字幕和正在播放的语音必须指向同一展示单元。
- 切换玩家时必须原子更新当前玩家、字幕容器和语音归属。
- 不得使用多个互不相关的 cursor 分别决定画面和语音。
- 字幕不得在语音结束后回退到上一句。
- 语音尚未开始时，不得因为未来事件提前展示下一位玩家正在发言。
- 非发言状态必须使用明确的裁判、等待或行动展示，不得沿用上一位玩家的发言状态。

## 8. 隐私准则

- 普通直播和上帝视角必须使用不同的服务端投影。
- 前端不得先接收完整秘密事件再自行隐藏。
- 狼队身份、狼刀目标、神职选择和查验结果必须默认失败关闭。
- 每新增一个细小环节，都必须分别验证普通直播和上帝视角能看到什么。
- 隐私验证未通过时，该环节不得进入用户验收。

## 9. 故障和超时准则

每个等待都必须有唯一责任方、明确起点、明确终点和可观测原因。

禁止：

- 用多个定时器竞争决定同一个状态。
- 用播放超时模拟正常完成。
- 超时后把旧语音重新插入当前队列。
- 因为语音失败而回退画面序列。
- 客户端断线导致全局游戏永久阻塞。

每个失败必须归类为模型、质量门、TTS、录音保存、传输、播放或状态协议失败，不能统一显示为“等待中”。

## 10. 最小开发单元

一次开发必须能用一句话描述，并且只产生一个新的可观察结果。例如：

- “Live V2 能展示当前对局的玩家座位快照。”
- “Live V2 能实时展示一条裁判字幕。”
- “Live V2 能播放一条裁判语音并在结束后进入空闲状态。”
- “狼人睁眼提示能在上帝视角出现，普通直播只显示夜晚等待。”

以下描述过大，不允许作为单次开发范围：

- “完成首夜。”
- “完成狼刀。”
- “完成神职功能。”
- “完成直播语音。”
- “完成断线恢复。”

## 11. 每一步的执行流程

### 11.1 开发前

必须先向用户提交：

- 本步唯一目标。
- 明确不做的内容。
- 将修改的模块。
- 事件输入与状态转换。
- 普通直播和上帝视角的预期表现。
- 画面、字幕、语音和结束条件。
- 自动化验证计划。
- 用户观察清单。

用户确认范围后才能实现。

### 11.2 实现后

必须提供：

- 实际修改文件。
- 自动化测试和结果。
- 一个真实的 `run_id`。
- 关键事件 ID 或展示序列。
- 用户需要观察的具体时间点和预期结果。
- 已知限制。

然后停止开发，等待用户本人观察。

### 11.3 用户验收后

- 用户未通过：继续当前环节，不能进入下一步。
- 用户通过：冻结当前契约和回归测试。
- 用户明确要求提交：创建只包含当前环节的本地提交，不推送。
- 用户明确允许下一步：再提出下一步的范围和验收标准。

## 12. 建议开发顺序

### 12.1 直播底座

以下每一项都是独立验收环节：

1. Live V2 独立路由和空页面。
2. 当前对局快照。
3. 只接收快照之后的新事件。
4. `presentation_seq` 去重和越序拒绝。
5. 单一当前展示单元。
6. 单条裁判字幕。
7. 单条裁判语音。
8. 字幕与语音引用同一个展示单元。
9. 展示单元明确结束并回到空闲。
10. 断线重连跳到当前快照且不补播旧语音。
11. 普通直播与上帝视角投影隔离。

底座没有全部通过前，不进入正式游戏阶段开发。

### 12.2 游戏开场

每一项单独验收：

1. 对局开始状态。
2. 玩家座位确认。
3. 角色和规则快照加载。
4. 裁判开场字幕。
5. 裁判开场语音。
6. 开场展示关闭。
7. 进入首夜的唯一状态转换。

### 12.3 首夜狼人阶段

“狼刀”继续拆分为：

1. 夜晚开始。
2. 狼人睁眼提示。
3. 狼队身份和隐私投影。
4. 狼人决策开始状态。
5. 单个狼人提交选择。
6. 多狼人选择的顺序与去重。
7. 狼队目标收敛。
8. 狼刀结果落库。
9. 普通直播不泄露狼刀信息。
10. 上帝视角展示最终狼刀结果。
11. 狼人闭眼提示。
12. 狼人阶段封口。
13. 只在封口后进入下一个角色阶段。

### 12.4 首夜神职阶段

一次只开发一个角色。每个角色继续拆分为：

1. 角色睁眼提示。
2. 角色行动开始。
3. 模型请求或选择等待状态。
4. 选择提交。
5. 规则合法性验证。
6. 结果落库。
7. 上帝视角结果。
8. 普通直播隐私投影。
9. 角色闭眼提示。
10. 角色阶段封口。
11. 封口后进入下一阶段。

预言家、守卫、女巫及规则配置启用的其他角色分别验收，不能打包开发。

### 12.5 天亮结算

神职阶段全部通过后，才逐项开发：

1. 夜间行动汇总。
2. 冲突规则结算。
3. 死亡结果落库。
4. 天亮提示。
5. 死亡公告字幕。
6. 死亡公告语音。
7. 玩家状态画面更新。
8. 首夜封口。
9. 进入白天。

## 13. 回归保护

每通过一个环节，都必须新增并保留对应不变量测试。至少覆盖：

- 序列单调递增。
- 重复事件幂等。
- 越序事件被拒绝。
- 同时最多一个当前玩家。
- A 未关闭时 B 不可激活。
- B 激活后迟到的 A 不可恢复。
- 字幕和语音属于同一分段。
- 保存语音和直播广播使用同一份 PCM、sample 数和校验值。
- 语音资产未保存完成时动作不可成功，保存失败明确停止。
- TTS 失败只推进一次。
- 重连不补播历史语音。
- 普通直播不包含秘密信息。

已经验收通过的行为不得在后续步骤中悄悄改写；如确需修改，必须重新说明影响并再次获得用户批准。

## 14. 每个新任务的开场模板

新任务必须先读取本文档，然后只处理用户指定的当前环节。建议使用以下指令：

> 阅读 `docs/live-v2-refactor-guidelines.md`，严格按照渐进式门禁执行。本任务只设计和实现一个最小环节。先核对现有代码与实际运行路径，然后提出本步范围、非范围、状态转换、自动化验证和人工观察清单。在我明确批准范围前不要修改代码；实现完成后提供真实 run_id 并停止，等待我本人观察。我没有明确回复“通过，进入下一步”之前，不得开发后续环节。不要修改旧直播页面来兼容 Live V2，不要开发 Replay，不要提交或推送代码，除非我明确要求。

每个新任务还必须执行 V2 旧业务零复用检查：不得导入、包装、复制或改名迁移旧游戏、模型、TTS、Live、Replay、记录或 UI 业务代码，只能使用第 3.3 节列出的运行基础设施。

## 15. 完成定义

单个环节只有同时满足以下条件才算完成：

- 代码范围符合批准内容。
- 自动化验证通过。
- 真实对局证据完整。
- 涉及公开语音时，对应 V2 语音资产已经保存并通过同源 PCM 校验。
- 画面、字幕、语音、时序和隐私均符合预期。
- 用户本人明确表示通过。

Live V2 只有在所有细小环节逐一通过后才算完成，不以“整局勉强跑通”作为完成标准。
